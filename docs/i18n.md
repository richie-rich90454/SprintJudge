# Internationalization

A small in-repo solution in `frontend/src/i18n/` — no additional dependency.

## Files

- `index.ts` — `I18nProvider`, `useI18n()`, `LOCALES`, `detectLocale()`,
  `applyStoredLocale()`.
- `en.ts`, `ar.ts` — flat `key → string` dictionaries. Arabic (`ar`) is the RTL
  locale.

## Usage

`App` wraps the router in `I18nProvider`, so any screen can call:

```tsx
const { t, locale, dir, setLocale } = useI18n();
return <button>{t("action.submit")}</button>;
```

`main.tsx` calls `applyStoredLocale()` before render so `<html lang>` and
`<html dir>` match the persisted locale on first paint. The choice is stored in
`localStorage` under `oq-locale`; `navigator.language` seeds the first visit.

Placeholders use `{name}`: `t("greeting", { name: "Ada" })`.

## Adding a locale

1. Add `xx.ts` exporting `Record<string, string>`.
2. Register it in `dictionaries` and add an entry to `LOCALES` in `index.ts`.
3. Set `dir: "rtl"` if the script is right-to-left; no CSS changes are needed.

## Fallback and scope

A missing key falls back to English, then to the key itself. The dictionaries
currently cover the platform chrome (skip link, route announcements, locale
switcher, update prompt) plus common navigation/action/status strings. Screen
text owned by other modules is migrated incrementally; unmigrated text stays in
its current language and is not broken by a locale switch.
